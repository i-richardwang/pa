# PA 时间合同

PA 把时间分成三层：用户声明要观察的业务期间；指标声明自己在时间桶上怎样求值；服务端把两者编译成带真实期间的结果。查询方只选择时间，指标怎样求值由指标自己决定；消费方直接读取结果里的期间，不根据指标名称或物理查询推断时间口径。

## 1. 查询时间：用户要看哪段期间

公开的时间参数由 `window` 和可选的 `comparison` 组成。输入格式以
[`TIME_INTENT_INPUT`](../server/src/semantic_core/time_contract.ts) 为准，本文只说明代码里看不出的业务含义。

- `window` 同时决定观察期间和输出粒度。单月查询只有一个结果桶；多月或多年的期间按声明的月或年粒度输出一个序列。
- 相对窗口以数据源的 `actual_through`（数据实际更新到的月份）为终点，随数据更新向前推进；指定了具体月份或起止月的窗口固定不变。
- `previous_period` 指紧邻的上一段等长期间；`previous_year` 指去年同月或去年同期。长度不同的期间只能用明确指定的自定义对照，这种对比称为"基准比较"，不叫同比或环比。
- YTD（年初至今）是一种查询窗口：从当年一月到窗口终点月。它的去年同期是把整个窗口往前移一个日历年。
- 整段期间的汇总值放在结果的合计（totals）里，与序列的输出粒度无关。月度或年度序列也可以同时带一个由服务端计算的整段合计。

时间参数只解析一次。基础结果、构成占比的分母、总体值和 Top-N 排名都使用同一份解析后的业务时间坐标；后续步骤只使用这份坐标，不重新解释用户输入。

## 2. `time_contract`：指标怎样在时间上求值

每个公开指标，以及运行时会用到的内部指标，都必须声明：

```yaml
meta:
  time_contract:
    aggregation: sum | average | last | recompute
    window: selected | year_to_date
    grain: month # 可选
```

各字段的含义：

| 字段 | 含义 |
|---|---|
| `aggregation: sum` | 在目标业务桶内求和。 |
| `aggregation: average` | 在目标业务桶内求平均。 |
| `aggregation: last` | 取目标业务桶最后一个月的值。 |
| `aggregation: recompute` | 先汇总各组成部分，再按指标公式重新计算；不对已经算好的比率求平均。 |
| `window: selected` | 使用用户选择的业务桶。 |
| `window: year_to_date` | 在每个业务桶的最后一个月，取当年一月到该月的累计值或在册结果。 |
| `grain: month` | 指标只在单月桶上有定义；查询跨多个月时必须按月输出。 |

`window: year_to_date` 和 `grain: month` 不能同时声明。比率指标的时间合同从它的组成指标逐层推导；如果组成指标推不出唯一的业务期间，语义包加载失败。

指标的时间合同在公共目录里表现为两个字段，二者回答不同的问题，不能互相代替：

| 公共字段 | 回答的问题 |
|---|---|
| `time.value_basis` | 指标值实际覆盖业务桶里的哪一段时间。 |
| `time.constraints` | 用户可以选择哪些时间粒度和对照方式。 |

`value_basis` 有三种取值：

| 取值 | 实际覆盖的期间 |
|---|---|
| `bucket_end` | 业务桶的最后一个月。 |
| `whole_bucket` | 整个业务桶；具体是求和、求平均还是重算比率，由指标合同决定。 |
| `year_start_to_bucket_end` | 业务桶最后一个月所在年份的一月到该月。 |

`constraints` 只描述选择上的限制：`grain: month` 表示跨月查询必须按月输出；`year_scoped` 表示整段合计不能跨日历年；`comparison: explicit_only` 表示该时间源只接受明确指定的自定义对照。某个值覆盖哪段期间，由 `value_basis` 回答，`constraints` 不回答。合计也遵循这一点：声明了 `grain: month` 的指标在跨月查询中没有整段值，合计改为取终点月的值，并标记 `degraded`。

## 3. 时间来源由语义包声明

`semantic_package.yml.time_sources` 定义各个业务时钟以及它们之间的关系。每个包必须有且只有一个主时钟。计划类时间源可以引用一个实际类时间源，以它的数据截止月作为边界。比较策略有两种：`calendar` 允许按日历平移得到上一期和去年同期；`explicit_only` 只接受明确指定的期间，适用于不应按日历自动匹配的观测数据（例如调研）。

稀疏数据是否补成逐月状态，由语义包的数据建模决定。补齐后，每个月的值表示该月末或之前最近一次的状态；数据批次（例如调研期次）仍作为业务维度公开。

## 4. 结果如何公开业务时间

直接查询的结果里，`view.time` 给出服务端最终采用的粒度、主期和对比期坐标，以及带业务键的时间桶。`view.column_time_basis` 为每个指标列声明求值基准，它和时间桶一起确定每个单元格对应的真实期间。`view.totals` 只包含实际的起止月和可选的 `degraded` 标记，求值基准沿用所属指标列的。

派生结果里，直接取自某个来源指标的列沿用该指标的求值基准；由公式计算出的列通过 `provenance` 说明各来源的期间。如果几个来源无法合成一条统一的业务时间轴，结果会逐列标明来源期间，不拼凑出一条合并的时间轴。

指标的物理时间窗口、求值方式、子查询数量和 Cube 时间成员都不属于公共协议。前端根据结果里的时间坐标组织时间轴和对比系列，不根据列名、指标名或数据值推断哪一列是时间，也不自行对指标做运算。

更换指标的物理绑定后，标题、导出、明细和公共列标识必须仍然表示同一个业务含义；数值相同不代表含义相同。
