# 代码与仓库内容质量标准

每次变更完成后按本标准清理仓库。架构、业务口径、前端样式和开源边界的规则见 `AGENTS.md` 和对应的专项规格。

## 内容分类

对本次 diff 和受影响的内容逐项分类：

| 分类 | 判定 | 处理 |
| --- | --- | --- |
| KEEP | 当前仍然成立，且从代码结构看不出来的约束、理由或公开合同 | 保留在它唯一的位置 |
| MOVE | 内容正确，但放错了层级或位置 | 移到正确位置，删除原文 |
| EXECUTABLE | 可以用 schema、类型、共享常量、lint 或行为测试自动检查 | 改写成可执行的检查，删除重复的文字 |
| DELETE | 历史过程、被否决的方案、复述代码、重复定义、为已删除功能留的说明、过期计划、注释掉的代码或一次性排查记录 | 直接删除 |
| REVIEW | 含义不确定，或可能影响业务行为、公开 schema、指标、权限、默认口径、对外文案或授权归属 | 保持原样并列出，交人工决定 |

清理不得改变业务行为、公开合同、指标定义、权限或默认口径。

## 检查内容

### 代码与配置

- 未使用的导入、导出、参数、状态、分支、类型、依赖和配置。
- 重复实现、多余的适配层、只为旧调用方式保留的兼容代码。
- 没有启用的备选方案、提前设计的扩展点，以及当前没有使用方的抽象。
- 代码、配置、容器、构建脚本和 CI 之间路径、命令、版本和入口的不一致。

### 注释与文档

删掉一条注释后，会不会有人因此把代码改错？不会就删。只保留四类：

| 保留 | 原因 |
| --- | --- |
| 外部行为 | 库、宿主环境或语言的行为不在本仓库里，读者无处可查 |
| 跨位置的关联 | 两处必须一起修改，或顺序不能调换，代码结构本身看不出来 |
| 业务口径 | 类型表达不了的业务含义，例如谁减谁、是否包含某类人员 |
| 特殊取值的来源 | 某个不直观的数值从哪里来、在哪里测得 |

注释默认一行，只写约束，不写推导过程。可能被打破的前提写成断言，不写在头注释里。

文档只描述当前可用的设计和用法，每条规则只写在一处。删除描述方案演变的内容（"以前""不再""已删除"）、过期 TODO、排查记录，以及与代码、类型或上级规格重复的解释。

### 测试与示例

- 测试名和断言描述当前行为，不保留已删除实现的名字，也不把已删除的符号列成永久禁用名单。
- 优先测试输入输出、公开类型和用户看得到的结果。只有架构边界无法通过行为观察时，才扫描源码；源码扫描必须带反向自检（已知的违规样本必须被发现）。
- Demo 和测试夹具只体现当前的公开能力。

## 流程

1. 阅读完整的 diff，而不只是最后一次提交。
2. 找出已删除或改名的符号、功能名称、路径和配置键，用 `rg` 全仓搜索受影响的引用。
3. 阅读改动文件的上下文，按上面的分类处理；REVIEW 项只列出。
4. 运行相关测试，再运行 `cd server && bun run check`。修改了语义模型的，再加跑 `AGENTS.md` 规定的模型回归测试。
5. 重新执行第 2 步的搜索，阅读最终 diff。
